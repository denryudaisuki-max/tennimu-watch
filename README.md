# チケット監視 → LINE通知

GitHub Actions で5分ごとにチェックし、**条件を満たしたら LINE に通知**します。
PC は閉じていて構いません。

## 監視している内容

| 項目 | 条件 |
|---|---|
| 公演 | ミュージカル『新テニスの王子様』The Final Stage |
| 対象 | **ページに出ている全公演**（公演日を過ぎたものは自動で除外） |
| 見ている受付 | すべて（一般発売・当日引換券・キャンセル待ちなど種類を問わない） |
| 通知条件 | どれかの受付が **「予定枚数終了」→「受付中」** に変わったら |
| 特別扱い | **2026/11/15(日) 17:30** が復活したときは通知を目立たせる |

公演を個別に書く必要はありません。ページに載っている公演をすべて見ます。

### 11/15(日)17:30 の特別扱い

この公演が復活したときだけ、通知の冒頭が変わり、一覧の先頭に `★` 付きで出ます。

```
🔔🔔🔔 お待ちかねの公演です 🔔🔔🔔

★ 2026/11/15 17:30　Kanadevia Hall（東京都）
　が復活しました！

──────────────
```

他の公演だけが復活したときは、通常の `🎫 チケットが復活しました！` で始まります。

`HIGHLIGHT` に足せば、目立たせる公演を増やせます。
また、この公演がまだ公演日前なのにページから消えた場合は、異常として警告を出します。

いずれも「条件を満たさない → 満たす」に変わった瞬間だけ通知します。
同じ状態が続く間は再通知しません。

> 以前はホテルの空室監視（東横イン札幌・東横イン大阪ドーム前・ルートイン土岐・
> ハートンホテル西梅田）と、テニミュ大阪公演の当日引換券も見ていましたが、
> いずれもユーザーの指示で削除しました（最後は 2026-10-31）。
> 復活させるなら git 履歴から戻せます。各サイトのAPIの要点は
> `handoff.sh` の引き継ぎ事項1にまとめてあります。

## 何を見ているか

イープラスの**公開の公演詳細ページ**を取得し、公演ごとの受付ステータスを読みます。

```
GET https://eplus.jp/sf/detail/0473460021
→ 39公演ぶんの「受付中 / 予定枚数終了 / 受付終了」
```

### 「イープラスは自動取得できない」との関係

過去にそう結論づけましたが、それは**席種別の在庫**の話です。取れる範囲が違います。

| 対象 | 取得 | 分かること |
|---|---|---|
| 公開の公演詳細ページ `/sf/detail/xxx` | **できる** | その公演が買える状態か |
| 申込ページ（`/sf/dvcjudge` の先） | できない | どの席種が何枚残っているか |

申込ページは Akamai と飛込防止（`DVC_UNIQUE_ID`）に阻まれ、今も自動取得できません。
今回は「復活したかどうか」が分かれば足りるので、公開ページだけで目的を達します。

### ファンクラブ枠（TSC当日引換券）は監視できません

テニミュ サポーターズクラブの当日引換券は、**一般発売とは在庫がまったく別枠**です。
TSC が「×（予定枚数終了）」でも、一般発売は受付中ということが実際に起きます。

| ページ | 載っている受付 |
|---|---|
| 公開ページ `eplus.jp/sf/detail/0473460021` | 先着一般発売 ／ 抽選イープラス先行 |
| TSCページ `w1.onlineticket.jp/sf/tkt18/detail/0473460021?P6=364` | 先着テニミュ サポーターズクラブ当日引換券 |

TSC の受付は**公開ページに1件も載りません**。TSCページを取りにいくと、会員番号6桁と
パスワードを求めるログイン画面（約6KB）しか返りません。会員としてログインし続ける必要が
あるため、このbotでは監視しません。

### 「当日引換券」は2種類あります。混同しないこと

名前が似ていますが別物で、**一方は監視でき、一方はできません**。

| 受付名 | どこに載るか | 監視 |
|---|---|---|
| `先着当日引換券受付` | **公開ページ** | **できる**（いま大阪の土日で見ているのはこれ） |
| `先着テニミュ サポーターズクラブ当日引換券` | TSC会員ページのみ | できない（会員ログインが必要） |

### 受付ごとに見ています

1公演に受付が複数あります（一般発売／抽選先行／当日引換券／キャンセル待ち）。
`TARGETS` に `uketsuke` を書くと、**名前にその文字を含む受付だけ**を見ます。
書かなければ全受付が対象です。

```python
{"date": "2026/10/24", "time": "17:30", "uketsuke": "当日引換券"}
```

これを入れずに全受付を混ぜて見ると、「一般発売が受付中」になっただけで
「当日引換券が復活した」と誤通知します。

### 同じ公演が複数ブロックに分かれて載ります

これにハマりました。公演詳細ページは、受付の種類ごとに別ブロックで同じ公演を出します。

```
2026/10/17 17:30 ブロックA → 先着一般発売 / 抽選イープラス先行
2026/10/17 17:30 ブロックB → キャンセル待ち券受付 / 先着当日引換券受付
```

日付ブロックの数（`block-ticket-fixed__date` の出現回数）は**公演数ではありません**。
同じ日時のブロックを1件にまとめないと、先に見つかったブロックの受付しか見えず、
当日引換券を永久に取りこぼします。`parse_performances` の最後でまとめています。

### HTML の読み方（実測）

公演1件ごとに `block-ticket-fixed__date` で始まるブロックがあり、その中に開演時刻・会場と、
受付ごとの `ticket-status__item` が入ります。1公演に受付が複数あるため状態は配列で持ちます。

```html
<div class="block-ticket-fixed__date"><span>2026/</span><span>11/15(日)</span></div>
<span class="block-ticket-fixed__time">開演：17:30～</span>
<span class="ticket-status__item ...">予定枚数終了</span>
```

**クラス名で判定してはいけません。** `ticket-status__item--accepting` は「予定枚数終了」にも
付いています。必ずテキストで見ます。

### 黙って見逃さないための作り

ページの作りが変わると、気づかないまま「ずっと復活しない」と誤報し続ける危険があります。
そこで次の3つはすべて**失敗**として扱い、3回続いたら LINE に警告を出してジョブも失敗させます。

- ページの取得自体に失敗した（遮断など）
- 公演を1件も読み取れなかった（HTML の作りが変わった）
- **まだ公演日が来ていない**対象が一覧から消えた

公演日を過ぎた対象は、ページから消えるのが当たり前なので失敗にしません（自動で見送ります）。
`TARGETS` から消し忘れても壊れません。

また、ある対象が見つからなくても**他の対象の判定と通知は続行します**。
以前はここで処理を打ち切っていたため、終わった公演が1件あるだけで
残りの公演の通知がまるごと止まるという不具合がありました（2026-10-15 修正）。

なお、**2週間おきに1〜2時間ほど取得に失敗します**。実測では 09/02 と 09/16 の
05:15〜07:05 JST に19〜22回連続で失敗し、どちらも自動復帰しました。イープラス側の
定期メンテとみられます。サイト自体が止まっている時間帯なので取りこぼしの実害はありませんが、
月に1〜2通この警告が LINE に届きます。

## ローソンチケットは監視できません（2026-10-16 決着）

ローチケでも当日引換券を見たかったのですが、bot 対策で届きませんでした。

| 試した方法 | 結果 |
|---|---|
| 手元の curl（HTTP/2） | `INTERNAL_ERROR` |
| 手元の curl（HTTP/1.1） | タイムアウト |
| 手元の Python urllib | タイムアウト |
| 手元の実ブラウザ（住宅IP） | **読める** |
| Actions のヘッドレス Chrome（HTTP/2） | `ERR_HTTP2_PROTOCOL_ERROR` |
| Actions のヘッドレス Chrome（HTTP/1.1） | タイムアウト |

Playwright を入れ、プロトコルも HTTP/1.1 に変えて試しましたが、どちらも通りませんでした。
通るのは住宅IPの実ブラウザだけで、IPで判定されているとみられます。
これ以上はブラウザ指紋の偽装か住宅用プロキシが必要で、転売対策の回避にあたるため行いません。

`check_lawson.py` は残していますが**本番ループには組み込んでいません**。
ローチケ側の対策が変わったときに「1回だけ実行（手動）」から再検証できます。

### 仮に通っても粒度が足りません

ローチケは受付単位でしか状態を持ちません。ページ内のJSONは当日引換券が1件だけです。

```json
{"receptionName":"当日引換券","entryStatusName":"予定枚数終了",
 "receptionDateEnd":"20261025 1830"}
```

カレンダーに公演日（10/17〜10/25）は並びますが、**状態は大阪全公演まとめて1つ**で、
公演ごと・土日のみの絞り込みはできません。
その用途はイープラス側（`check_tennimu.py`）が担当していて、そちらは公演ごとに見ています。

## なぜ cron を使っていないのか

**GitHub の cron は当てになりません。** `*/5` と設定していた時期の実測値です。

```
想定       855回（5分ごと・71時間）
実際        59回          実行率 7%
間隔の中央値  59分
最短間隔     16分   ← 一度も5分を達成していない
最長間隔    208分   ← 3時間28分の空白
```

そこで、**1つのジョブを5時間30分走らせ続け、その中で自前のタイマーで5分ごとに確認**します
（`watch_loop.sh`）。cron は「ループが途切れたときに再開させるトリガー」に格下げしています。

ループ中に届いた起動要求は `concurrency` によって「待機中」として1件保持され、
ループが終わった瞬間に次のループが始まります。これで切れ目なく続きます。

外部サイトへのリクエストは5分に1回のまま、それが実際に守られるようになります。
増えるのは GitHub 側の計算時間だけで、パブリックリポジトリなので無料です。

## 条件を変えるには

`check_tennimu.py` 先頭の定数を書き換えます。

```python
EVENT_URL = "https://eplus.jp/sf/detail/0473460021"   # 公演詳細ページ
TARGETS = [
    {"date": "2026/11/15", "time": "17:30"},
]
```

`TARGETS` は増やせばまとめて見ます。**公演日を過ぎた対象は自動で見送る**ので、
消し忘れても壊れません。別の公演にするときは `EVENT_URL` をその興行のものに変えます。

## セットアップ（設定済み）

- リポジトリは **Public**。5分間隔だと月およそ8,600分になり、プライベートの無料枠（月2,000分）では
  1週間で尽きます。パブリックなら Actions は無制限・無料です
- LINE のトークンは `LINE_CHANNEL_ACCESS_TOKEN` という名前の Secret に登録済み
- Bot を LINE で友だち追加済み（これがないと送信は成功扱いでも届きません）

## 動作確認

**Actions タブ → 「空室監視」→ Run workflow** で手動実行できます。

### 通知テスト

「1回だけ実行（手動）」に `notify=true` を渡すと、LINE まで通して試せます（下記）。
ただし現在の状態が「受付中」でないと通知は飛びません。

### Actions 上で1回だけ走らせる（疎通確認）

**Actions タブ →「1回だけ実行（手動）」** で、監視スクリプトを1回だけ実行してログを読めます。
「手元では取れるのに GitHub の IP からは弾かれる」を見つけるためのものです。

```bash
gh workflow run "1回だけ実行（手動）" --repo denryudaisuki-max/tennimu-watch \
  -f script=check_tennimu.py -f notify=false
```

既定では LINE に送らずログに出すだけです。`-f notify=true` で実際に送信します。
これも監視ループとは `concurrency` グループが別なので、ループは止まりません。

## 注意点

- **瞬間的に出て消える部屋は取りこぼす可能性があります**（5分間隔のため）
- **リポジトリが60日間無活動だとスケジュールが自動停止します。** 状態変化時は自動コミットされるので、
  通常は問題になりません
- LINE の無料枠はコミュニケーションプランで**月200通**。超過しても課金はされず、送信できなくなるだけです。
  5分ごとのチェック自体は1通も消費しません
- データを取得できない状態が3回続くと、警告を LINE に送り、ジョブも失敗させます
  （GitHub から障害メールが届きます）

不要になったらリポジトリを削除するか、Actions タブでワークフローを Disable してください。
